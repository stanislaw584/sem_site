# Технический подход

## Рекомендуемый стек

Для MVP лучше всего подходит статический frontend:

- Vite;
- React;
- TypeScript;
- React Router;
- Tailwind CSS;
- MDX или структурированный JSON/YAML для контента;
- статический хостинг: GitHub Pages, Netlify, Vercel или сервер университета.

Такого стека достаточно, потому что сайт информационный, не требует авторизации и не работает с персональными данными.

## Почему не нужен бэкенд на старте

Бэкенд не нужен для первой версии, потому что:

- контент можно собирать в статические страницы;
- нет личных кабинетов;
- нет персональных данных;
- поиск откладывается;
- статический сайт проще, дешевле и безопаснее развернуть.

При этом архитектура должна сразу готовить проект к будущему редактированию контента не разработчиком.

## Как хранить контент

Рекомендуемый подход для MVP:

- хранить контент в папке `/content`;
- один файл = одна статья;
- в начале файла хранить метаданные: заголовок, раздел, язык, порядок, связанные статьи, дата проверки, контакты;
- отображать контент через React-компоненты.

Пример метаданных:

```yaml
---
id: activate-account
category: start
lang: ru
title: Активировать личный кабинет ДВФУ
summary: Получите доступ к "Мой Универ", почте и цифровым сервисам.
contacts:
  - sem-admin
  - it-support
lastReviewed: 2026-05-01
---
```

## Как потом дать редактирование менеджеру

Варианты:

1. Decap CMS - редактор меняет Markdown/MDX через удобную админку, изменения сохраняются в Git.
2. TinaCMS - визуальное редактирование контента с сохранением в Git.
3. Notion или Google Sheets как временный источник контента.
4. Strapi или Directus, если позже понадобится полноценная CMS с ролями и базой данных.

Рекомендуемый путь:

- MVP: контент в MDX/JSON внутри проекта.
- Следующий этап: Decap CMS или TinaCMS.
- Позже: headless CMS, только если контента станет много и появится сложный процесс согласования.

## Мультиязычность

Структуру языков нужно заложить сразу:

```txt
content/
  ru/
    start/
      activate-account.mdx
  en/
    start/
      activate-account.mdx
  zh/
    start/
      activate-account.mdx
```

В интерфейсе:

- язык должен быть в URL: `/ru`, `/en`, `/zh`;
- если перевода нет, можно временно показывать русский или английский вариант;
- в будущем можно добавить статус "нужен перевод" для редакторов.

## Поиск

В MVP можно оставить поле поиска как визуальный элемент и задел на будущее. Основная навигация на первом этапе - карточки и разделы.

Варианты поиска на следующих этапах:

- Pagefind - хороший вариант для статического сайта;
- Fuse.js - локальный поиск по небольшому набору статей;
- Algolia - если позже нужны аналитика, быстрый поиск и внешний сервис.

Рекомендация: после MVP добавить Pagefind, потому что он не требует бэкенда и хорошо подходит статическим сайтам.

## Основные UI-компоненты

- `AppHeader`
- `LanguageSwitcher`
- `CategoryCard`
- `ArticleList`
- `ArticlePage`
- `ContactBlock`
- `RelatedLinks`
- `Footer`

Для иконок лучше использовать `lucide-react`.

## Визуальное направление

Интерфейс должен быть близок к приложенному макету:

- чистый белый фон;
- спокойный синий акцент;
- сетка карточек в 2 колонки на desktop;
- одна колонка на мобильных;
- понятная типографика;
- минимум декора;
- без тяжелых иллюстраций.

Карточки стоит использовать для разделов и списков статей. Страницы статей должны быть чистыми и удобными для чтения, без лишних вложенных карточек.

## Доступность и удобство

Обязательно:

- адаптивная верстка;
- правильные заголовки;
- доступные с клавиатуры ссылки и переключатель языка;
- хороший контраст;
- копируемый текст;
- понятные focus-состояния;
- отдельный title для каждой страницы.

## Деплой

Рекомендуемый MVP-деплой:

- GitHub-репозиторий;
- сборка через `npm run build`;
- публикация через Vercel, Netlify или GitHub Pages.

Если университет требует внутренний хостинг, результат сборки можно отдать как обычные статические файлы.
